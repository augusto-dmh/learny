## The finding that was deliberately not posted

The performance lane examined whether `RunIngestion.begin_run`'s read-modify-write on `attempts` is atomic, found that it is not, and chose not to post because it could not reach its confidence bar. **Verified independently rather than inherited**, because the `v6-page-unit` cycle's single most severe finding arrived by exactly this route — an unposted cross-lane note about a stale read feeding a durable counter — and turned out to be real.

Confirmed non-atomic: `SqlAlchemyIngestionJobRepository.get_by_id` is a plain `SELECT` with no `FOR UPDATE` (`repositories.py:300`) and `update` writes a Python-computed `attempts` (`:315`), so under READ COMMITTED two concurrent claims would produce a classic lost update.

**Judged not a defect, and materially unlike the `v6-page-unit` case.** There, the lost update corrupted a durable *accumulating* counter that nothing recomputes, leaving permanently wrong data. Here `attempts` is a bounded *guard*: a lost update delays termination by one attempt and self-corrects, because the next claim re-reads the persisted value. It cannot cause the cap to fail to fire, and it cannot corrupt anything. Reaching the concurrency at all requires two simultaneous claims of the same job, which the `visibility_timeout (3600) > task_time_limit (1800)` ordering exists to prevent — the very relationship WRK-06 now pins by test. Recorded here rather than dropped silently, because "we checked this and here is why it is safe" is worth more than absence.

## What the review confirmed rather than faulted

Worth recording because it is evidence about the cycle, not praise: the cap landed in the application layer with no Celery type, `self.request`, or broker concept crossing the boundary, and both composition roots changed by exactly one line with no second literal introduced; `_exhaust` writes the same transitions as the ordinary failure path; `visibility_timeout > task_time_limit` is a genuine relationship rather than two literals; the restore path cannot reach the live database **by construction** (the sidecar never mounts `db_data`); every out-of-scope item is genuinely absent; `pyproject.toml`/`uv.lock` are untouched; and a mechanical cross-check of every `LEARNY_*` name across the runbook, ADR and specs against the shipped code found **zero fabricated names** — the failure mode this project recorded from an earlier cycle.
